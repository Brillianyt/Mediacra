# 结构化生成任务中心 Roadmap

## 目标

将当前“生成/刷新结构化”的同步长请求，演进为可持续运行的后台任务系统，解决以下问题：

- 点击生成时 WebUI 全局卡顿
- 批量结构化缺少进度、失败明细与取消能力
- 图片处理、结构化抽取、质量评分、远程同步耦合过深
- 当前实现不利于扩展、限流、重试和断点续跑

## 总体原则

- 先止血，再解耦，再产品化，最后平台化
- 每个阶段都必须可以独立上线、独立验收
- 不再继续新增同步长耗时 HTTP 接口
- 所有重型处理必须围绕最终的“结构化任务中心”建设

## 阶段规划

### 阶段 1：止血与边界收拢

目标：

- 点击“生成/刷新结构化”后立即返回
- Web 进程不再直接串行跑整批结构化
- 把路由中的结构化核心逻辑抽到 service 层

主要任务：

- 将当前 `materialize_from_db` 改为“创建任务”接口
- 抽离结构化执行器 service，统一输入输出对象
- 为任务建立最小状态机：`pending / running / success / failed / cancelled`
- 保留现有功能语义，避免大规模业务回归

验收标准：

- 生成结构化时其他页面仍可正常使用
- 用户可查看任务状态
- 不再出现整个 WebUI 因单次结构化而明显冻结

### 阶段 2：任务中心与专用模型

目标：

- 正式建立结构化任务的业务模型
- 让整批任务和单条任务都可见、可追踪、可重试

主要任务：

- 新增 `StructuredJob`
- 新增 `StructuredJobItem`
- 将处理链路标准化为以下步骤：
  - 取源记录
  - 图片准备与本地化
  - 图片理解
  - 图文联合结构化抽取
  - 质量评分
  - 结构化入库
  - 可选远程同步
- 为 Job 和 Item 增加耗时、错误、结果、版本字段

验收标准：

- 可查看总进度、成功数、失败数、跳过数
- 可查看单条失败原因
- 整批中部分失败不会导致全部失败

### 阶段 3：独立 Worker 与受控并发

目标：

- 执行彻底脱离 Web 进程
- 建立稳定的批处理能力

主要任务：

- 新增独立 `structured_worker`
- 基于 DB 任务表消费任务
- 为 LLM 调用、图片下载和入库分别设置并发与限流
- 支持超时、重试、退避、幂等和断点续跑

验收标准：

- Worker 可独立运行
- Worker 重启后任务可恢复
- 长时间任务运行期间 WebUI 依旧流畅

### 阶段 4：产品化与运维化

目标：

- 将结构化任务系统建设为可运营、可观测的能力模块

主要任务：

- 前端新增任务中心页面
- 支持查看任务、日志、失败项、取消、重试
- 增加耗时统计、成功率、失败原因分布
- 将远程同步纳入统一流水线
- 增加治理能力：最大并发、清理策略、告警策略

验收标准：

- 业务侧可自行定位失败原因
- 结构化任务不再依赖开发人工盯日志

## 当前执行策略

当前默认推进顺序：

1. 阶段 1
2. 阶段 2
3. 阶段 3
4. 阶段 4

说明：

- 本 Roadmap 的最终目标与阶段顺序不变，本轮调整仅优化执行路径，不改变终局形态
- 最终仍然要落到“结构化任务中心 + 独立 Worker + 可观测治理 + 产品化任务中心”
- 当前优化的核心是避免在阶段 2.5 反复投入低收益重构，而是尽快进入阶段 3 的最小可运行形态

当前实现与后续开发都应遵守以下约束：

- 不在 FastAPI async 路由中直接执行同步阻塞的 LLM 调用
- 结构化图片统一落本地 `data/structured_images`
- 结构化高分筛选与源表评分必须明确区分
- 结构化任务应优先支持查询、取消、重试，而不是继续增强同步接口

## 当前进展评估

### 已完成

- 阶段 1 已完成：
  - “生成/刷新结构化”已改为创建任务后立即返回
  - WebUI 已具备最小任务状态展示与轮询能力
  - 路由层与执行编排已初步拆分，核心执行流程已迁移到 service/helper
- 阶段 2 已基本完成：
  - 已有 `StructuredJob` / `StructuredJobItem`
  - 已有任务状态、进度计数、失败原因、取消能力
  - 已有结构化缓存写入、本地图片缓存与结果展示闭环

### 未完成

- 阶段 2 尚未完全补齐：
  - `Job` / `Item` 维度的耗时、版本、治理字段仍不完整
  - 重试、恢复、幂等仍未成体系
- 阶段 3 尚未真正开始：
  - 当前执行仍依赖 Web 进程内 `asyncio` 任务
  - 尚无独立 `structured_worker`
  - 尚无 `claim / heartbeat / lease / recovery` 机制
- 阶段 4 仅有局部雏形：
  - 当前只有结构化页面中的任务卡片
  - 还没有独立任务中心、失败重试面板和治理视图

## 计划优化说明

本轮调整结论：

- 调整符合既定最终计划
- 调整不改变阶段目标，只改变当前阶段的推进重心
- 调整后的核心原则是“停止低收益的纯瘦身重构，转向为独立 Worker 建立最小可运行能力”

具体优化如下：

1. 保持阶段 1、阶段 2 的成果冻结
   - 除缺陷修复外，不再回头重做已验收功能
   - `ai.py` 的继续瘦身不再作为主目标，只保留与 Worker 解耦直接相关的拆分

2. 将阶段 3 拆为两个子阶段
   - 阶段 3A：最小独立 Worker
   - 阶段 3B：受控并发与治理增强

3. 将阶段 4 的完整任务中心后移
   - 在 3A 稳定前，不优先投入完整任务中心 UI
   - 先确保执行真正脱离 Web 进程，再做运营化和可视化增强

4. 当前的主攻方向从“代码位置重构”切换为“执行可靠性建设”
   - 先解决任务领取、租约、心跳、恢复
   - 再补并发控制、限流、超时、重试和断点续跑

## 优化后的实施顺序

### 阶段 3A：最小独立 Worker

目标：

- 在不改变现有任务接口与前端交互方式的前提下，让执行脱离 Web 进程

主要任务：

- 继续下沉 `_analyze_activity_request` 相关依赖，形成 Worker 可直接调用的执行单元
- 为 `StructuredJob` 增加 Worker 消费所需字段：
  - `worker_id`
  - `heartbeat_at`
  - `lease_until`
  - `attempt_count`
  - `next_run_at`
  - `last_error_stage`
- 新增最小可运行的 `structured_worker`
- 基于 DB 任务表实现 `pending -> claimed -> running -> finished` 的消费闭环

验收标准：

- Worker 可独立启动并消费任务
- Web 进程重启不会导致正在等待的任务丢失
- 任务执行不再依赖进程内 `asyncio.create_task`

### 阶段 3B：受控并发与治理增强

目标：

- 将“能跑”提升为“稳定可恢复可治理”

主要任务：

- 增加 LLM、图片下载、写库三个维度的并发与限流
- 增加超时、退避重试、幂等保护
- 增加 lease 超时回收与任务恢复
- 增加清理策略与历史任务归档策略

验收标准：

- Worker 异常退出后任务可恢复
- 连续批量运行时 WebUI 与数据库压力可控
- 任务失败原因可被稳定归类

### 阶段 4：产品化与运维化

目标保持不变，但启动条件调整为：

- 阶段 3A 完成并稳定
- 阶段 3B 至少完成最小恢复与并发治理能力

这样可避免在底层执行仍不稳定时过早投入完整任务中心与运营界面

## 下一步实施清单

下一轮开发优先完成以下事项：

1. 继续下沉 `_analyze_activity_request` 相关依赖，减少 Worker 对 `ai.py` 的耦合
2. 为 `StructuredJob` 增加 `claim / heartbeat / lease / attempt` 相关字段
3. 新增最小可运行 `structured_worker`，按 DB 任务表轮询并执行 `pending` 任务
4. 补齐任务恢复与治理：超时回收、重试次数、幂等保护、并发上限
5. 在 3A 稳定后再补独立任务中心页面与失败重试入口
