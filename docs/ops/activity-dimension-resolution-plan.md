# 活动维表解析改造计划

## 背景

当前活动结构化链路已经能够完成：

- 爬虫采集
- 图文结构化分析
- 远程数据库插入

但远程活动库中的部分字段并不是直接存中文名称，而是使用维表外键 UUID：

- 城市使用 `city_id`
- 活动类别在目标库中也使用维表 UUID

现状中，结构化抽取阶段输出的是自然语言文本，例如 `上海`、`深圳`、`AI教学工坊`。如果不经过维表解析层，直接入库会产生以下问题：

- 名称无法直接满足外键约束
- 同义词、别名、英文名会导致匹配失败
- 解析失败时容易误写脏数据
- 后续扩展社区、主办方等维度时会继续重复同类问题

## 改造目标

建立统一的“维表解析层（Dimension Resolver）”，将结构化文本字段转换为目标库要求的 UUID，再执行远程插入。

目标原则：

- LLM 只负责语义抽取，不直接决定 UUID
- 程序负责标准化、别名归一和维表匹配
- 解析过程可审计、可回放、可逐步扩展
- 先解决城市，再推进类别和多标签关系

## 当前数据判断

基于 `DATABASE_TYPE` 目录中的样例：

- `activities_rows.csv` 已明确存在 `city_id`
- `cities_rows.csv` 提供了 `id/name/label/slug`
- `tags_rows.csv` 提供了 `id/name/slug/core`

由此可以确认：

- 城市维表解析可以立即落地
- 类别/标签更适合走统一标签维表解析框架
- 第一阶段应优先接通 `city -> city_id`

## 分阶段计划

### 阶段 1：接入城市维表解析

目标：

- 在远程插库前补齐 `city_id`
- 避免把无法解析城市的记录直接插入远程库

任务：

- 新增独立维表解析 service
- 支持城市名称、中文别名、英文名、slug 匹配
- 优先读取远程维表；不可用时回退到 `DATABASE_TYPE` 本地样例
- 在运行时插库前执行解析
- 对无法解析城市的记录返回跳过原因

验收：

- `上海`、`上海市`、`Shanghai` 可以稳定解析到同一个 `city_id`
- `线上`、`全国` 这类已存在维表值可以命中固定 UUID
- 解析失败的记录不会继续写入远程 `activities`

当前状态：

- 已开始开发
- 已新增 `dimension_resolver_service.py`
- 已接入 `structured_runtime_service.py` 的 MemFire 插库链路

### 阶段 2：补齐类别 / 标签解析

目标：

- 将 `category` / `tags` 文本统一映射到 `tags_rows.csv` 中的标准标签定义

任务：

- 统一 `category` 和 `tags` 的解析规则
- 将 `category` 规范为标签字典里的标准名称
- 将标签匹配结果保留为内部解析结果，供后续关系化写入复用
- 对未命中的类别输出审计信息

验收：

- 模型输出的固定标签能够稳定解析到既有维表记录
- 不再依赖自由文本直接写类别字段

当前状态：

- 已搭好标签字典解析基础能力
- `tags_rows.csv` 现作为活动标签字典来源
- 当前线上 `activities` 字段仍使用 `category` 文本，因此本轮以标准名称归一为主

### 阶段 3：别名治理与人工兜底

目标：

- 让解析能力从“能用”提升到“可持续维护”

任务：

- 增加城市别名字典
- 增加类别别名字典
- 增加解析失败审计日志
- 为 WebUI 提供待人工确认列表
- 人工确认后沉淀为新别名规则

验收：

- 新出现的城市/类别只需人工确认一次，后续可自动命中
- 维表不会继续被低质量自动创建污染

### 阶段 4：关系表和全链路治理

目标：

- 支持“主类目 + 多标签”完整入库
- 为后续社区、主办方等外键维度复用同一能力

任务：

- 若线上使用关系表，增加二阶段插入：
  - 先插 `activities`
  - 再插标签关系表
- 扩展解析器到 `community_id`、`organizer_id`
- 增加缓存刷新、失败重试、统计指标

验收：

- 活动主记录和维表关系记录可稳定落库
- 不同外键维度共用统一解析框架

## 已落实的本轮改动

本轮已完成以下基础建设：

- 新增 `api/services/dimension_resolver_service.py`
- 增加城市维表缓存与本地 CSV 回退
- 支持城市按 `label/name/slug` 解析
- 支持标签按 `name/slug/core` 解析
- 在 `insert_memfire_records()` 中增加了解析步骤
- 对城市解析失败的记录增加了跳过原因输出
- 在入库返回中增加维表解析统计与逐条解析明细，便于后续审计和规则治理
- 已增加未命中标签/类别的审计信息，为后续别名字典和人工确认提供输入样本

## 下一步执行顺序

1. 为解析层补充自动化测试
2. 验证真实远程库中的类别字段结构
3. 将类别 UUID 正式接入远程 payload
4. 如后续新增活动标签关系表，则补关系表写入逻辑
5. 增加别名表和人工确认机制

## 风险与注意事项

- 当前 `DATABASE_TYPE/activities_rows.csv` 中的列名是 `category`
- 通过读取远程 `activities` 实际数据，也确认当前线上暴露字段中存在的是 `category`，尚未直接看到 `category_id`
- `tags_rows.csv` 当前可视为活动标签字典本体，而不是已落地的活动标签关系表
- 因此类别部分本轮先做解析基础能力与标准名称归一，不直接强推远程写入 UUID 字段，避免误伤现有线上插库
- 历史数据中已出现 `Cityxxxxxx` 形式的城市记录，后续需要做一次维表清洗

## 建议的近期验收口径

- 城市解析成功率显著提高
- 远程入库返回结果中能看到明确的 `skipped_details`
- 远程入库返回结果中能看到 `dimension_resolution_details`
- 未命中的标签和类别能够在返回结果中被显式识别
- 解析失败记录不再静默落库
- 后续类别接入时不需要再重写整条插库链路
